# Wallet settlement and reconciliation revision

Base: user-uploaded `papertrade(3).zip`. Prior adaptive memory, risk rules, Terminal tabs and mobile changes retained. Source-only package. No deployment or live database connection occurred.

## Defects and changes

- `backend/paper_engine.py`: manual exit, target, stop-loss and square-off now converge on `_settle_position`; require an existing ACTIVE trade of the correct owner under a database wallet write lock; no insertion of a missing closed trade or repeat wallet credit. Compute premium and round-trip net P&L from persisted entry and quantity, credit once, and commit settlement and wallet together. Fill costs use the same two-decimal entry price as persisted trade records. Recompute stored reserve from ACTIVE trade premiums after fills/settlement. Pending fills require their persisted pending row; wallet mutations serialize on the account row (SQLite writer lock / PostgreSQL row lock). Reset also uses that lock. Existing process-local lock retained. These changes do not implement distributed market monitoring or guarantee multi-worker initial account creation.
- `get_state`: wallet, baseline and trade records read in one joined statement; database active/closed status drives history and reserve, with current local MTM quotes overlaid for matching active positions. Pending orders read separately from DB. New response fields `stored_margin` and `margin_discrepancy`; actual displayed reserve based on ACTIVE trade records. No historical cash repair during reads. Live MTM remains process-local; pending snapshot is a separate query. Reserve is the existing simplified paper premium model, not actual broker margin.
- `backend/wallet_accounting.py`: pure reserve and reconciliation preview helpers; check closed gross P&L and net-after-charges arithmetic. No attempt to recalculate historical statutory charges or infer unknown resets. 
- `frontend/src/components/Header.jsx`: distinguish stored margin discrepancy from cash/trade ledger difference.
- `backend/reconcile_wallet.py`: operator-only dry-run by default, explicit DB URL and user ID, fingerprint of reviewed ledger, explicit verified-ledger flag, refuses inconsistent records, active positions or pending orders. On approved apply, writes only the selected wallet and a before/after audit entry in `app_kv`, in one transaction. No schema migration needed. Does not modify trade records. Do not run against production until test database verification and ledger review succeed.
- `backend/tests/test_wallet_accounting.py` and `test_wallet_settlement.py`: offline and database regression coverage.

## Operator procedure

1. Back up Supabase, including portfolios, paper_trades, pending_paper_orders, and app_kv. Stop all trading workers/schedulers, cancel pending orders and close positions normally before maintenance. Test the new code and command against a restored disposable database first. Keep the production environment private.
2. Use the existing database connection in the operator's shell (set `DATABASE_URL` explicitly, not in chat or a committed file). Identify the numeric account ID from the users table. From backend, install requirements and run `python reconcile_wallet.py --user-id YOUR_NUMERIC_ID` (replace placeholder with actual ID). Preview does not write balances.
3. Check actual trade counts, starting capital, current-cycle baseline, past wallet resets, any cash adjustments, missing/duplicate trades, and net charges against independent records. If the ledger or baseline is incomplete, stop; reconstruct the missing records/baseline separately. A zero issues list only verifies basic arithmetic, not historical completeness. Missing baseline may represent older resets. Do not use `--verified-ledger` unless these checks are done.
4. Only if preview is independently verified, run `python reconcile_wallet.py --user-id YOUR_NUMERIC_ID --apply --verified-ledger --confirm YOUR_PREVIEW_TOKEN`. Use exact token output by preview; changes to reviewed trade/wallet records invalidate it. No active trades or pending orders allowed. The command records old and proposed amounts in app_kv under a unique wallet-repair key; retain audit output privately. Re-run preview to verify zero adjustments. Restore backup if an erroneous repair occurs (with all workers stopped and consideration of subsequent transactions).
5. Deploy revised backend and frontend after integration testing. Verify account display and a buy/exit, stop-loss, target, pending fill and reset on test account, including simultaneous exits, then resume paper trading. Never reset wallet simply to hide discrepancy.
